    阶段 01
    基础认知 · 4周 · 入门
    理解 LLM 技术栈与 AI 产品生态，建立正确认知框架
    📺
    📖 学习要点（5 条）
    Transformer 是 GPT/Claude/Llama 等所有主流大模型的架构基石，核心是「自注意力机制」。
    • 自注意力(Self-Attention)：让每个 token 直接关注序列中所有其他 token，通过 Q/K/V 三个向量计算注意力权重，解决长距离依赖问题。
    • 多头注意力(Multi-Head)：并行多组 Q/K/V，分别捕捉语法、指代、语义等不同子空间的关系。
    • 位置编码(Positional Encoding)：抛弃 RNN 时序后，必须用正弦/可学习向量告诉模型「词的顺序」。
    • 残差连接 + LayerNorm + 前馈网络(FFN)：保证深层网络可稳定训练的标准结构。
    • 关键收益：完全并行、训练快、长文本建模强——这是后续 Scaling Law 与预训练范式的前提。
    📺
    📖 学习要点（4 条）
    建立对 Claude 能力与边界的直观认知，比纯理论更贴近实战。
    • 课程通常覆盖：大模型能做什么/不能做什么、Prompt 基础、Tool Use 入门、Agent 概念。
    • 重点建立「能力边界」直觉：擅长生成与推理，不擅长精确计数、实时事实、处理保密信息。
    • 动手跑通每个示例，记录哪些任务模型表现好、哪些容易翻车。
    • 把术语沉淀成自己的词汇表（prompt / context window / token / system prompt …）。
    📺
    📖 学习要点（4 条）
    RAG 是让 LLM「用上外部知识」的最常用方案，核心是「先检索、再生成」。
    • 流程：文档切分(Chunk) → 向量化(Embedding) → 存入向量库 → 提问时检索 Top-K → 拼进 Prompt 让 LLM 回答。
    • 为什么用 RAG：弥补模型知识截止、减少幻觉、让答案可溯源。
    • 关键旋钮：切分粒度、Embedding 模型选型、检索召回率(Recall)、重排(Re-rank)、上下文压缩。
    • 局限：检索质量决定天花板；需配套评估检索命中与答案忠实度。
    📺
    📖 学习要点（4 条）
    用 PM 视角把零散概念串成一张技术栈地图，便于和工程/算法沟通。
    • 分层梳理：基础模型层(基座/微调) → 推理部署层(推理框架/量化) → 应用层(RAG/Agent/编排) → 评测层(Eval/监控)。
    • 每个层面对应「PM 要关心的决策点」：成本、延迟、可控性、可观测性。
    • 用一张图表达数据如何从原始文档流向用户答案。
    • 产出：一页笔记 + 一张架构草图，作为后续项目的参考基线。

    阶段 02
    核心技能 · 4周 · 核心
    Prompt 工程、Agent 设计、MCP 协议，掌握 AI PM 核心能力
    📺
    📖 学习要点（4 条）
    掌握面向 Claude 的高质量 Prompt 写法，这是 AI PM 的硬基本功。
    • 清晰的任务描述 + 角色设定(system prompt) + 输出格式约束。
    • 技巧：few-shot（给示例）、chain-of-thought（先思考再答）、结构化输出(JSON / XML)。
    • 善用官方工具：Prompt Generator 与 Prompt Library 直接套用成熟模版。
    • 原则：具体优于抽象；把「好答案长什么样」写清楚；用分隔符隔离指令与内容。
    📺
    📖 学习要点（4 条）
    Agent = 模型在「思考—调用工具—观察结果」的循环里自主完成任务。
    • Agent Loop：LLM 输出 tool_call → 系统执行工具 → 结果回灌上下文 → 模型决定下一步，直到完成。
    • Tool Use：把「查数据库/调 API/跑代码」封装成工具，模型只决定何时调用、传什么参数。
    • 关键设计：工具描述要清晰（模型靠描述决定用不用）、结果要可解析、要有终止条件防死循环。
    • Anthropic 官方强调「less structure, more tools」——多给工具，少写死流程。
    📺
    📖 学习要点（4 条）
    动手把 Agent Loop 跑通，比看文档印象深十倍。
    • 选一个真实小任务（如：根据一句话查询天气并生成提醒）。
    • 定义 1-2 个工具（function schema：name / description / input_schema）。
    • 实现循环：调用 Claude → 解析 tool_use → 执行 → 以 tool_result 回传 → 继续。
    • 验证：让模型在缺少信息时主动调用工具，而非编造答案。
    📺
    📖 学习要点（4 条）
    MCP(Model Context Protocol) 是「统一工具接口」标准，让 Agent 即插即用地连数据源/软件。
    • 角色：MCP Server 暴露资源(Resources)/工具(Tools)/提示(Prompts)；MCP Client（如 Claude Desktop）消费。
    • 价值：一次写好 Server，任意支持 MCP 的客户端都能用，避免重复对接。
    • 动手：用官方 SDK 写一个最小 Server（如读取本地文件/调一个 API），再接到客户端。
    • 注意权限与边界：Server 能访问什么、是否需用户确认后才执行写操作。
    📺
    📖 学习要点（4 条）
    把前几周的经验沉淀成可复用资产，是 PM 的「方法论库」。
    • Prompt 模版库：按场景分类（摘要/抽取/分类/对话/代码），每条记录有效写法与坑。
    • Agent 设计模式：ReAct(推理+行动)、Plan-Execute(先规划再执行)、Reflection(自我复盘)、Multi-Agent(分工协作)。
    • 每类模式记「适用场景 + 优缺点 + 你踩过的坑」。
    • 这份资产可直接进作品集，展示你的工程化思维。

    阶段 03
    实战项目 · 2周 · 实战
    独立完成一个端到端 AI 产品，从需求到 Eval 全流程
    📺
    📖 学习要点（4 条）
    用 PM 的方式定义一个「真的能用 AI 解决」的问题。
    • 选题三问：痛点真实吗？AI 是更优解吗？数据/工具可达吗？
    • PRD 要点：用户与场景、AI 能力边界假设、核心流程(Agent/RAG)、成功指标、风险与回退。
    • 重点写清「为什么不用传统规则方案」——体现 AI 的独特价值。
    • 产出：一份能给工程师直接开工的 PRD。
    📺
    📖 学习要点（4 条）
    把 PRD 落地成一个可演示的 Agent，验证技术可行性。
    • 设计 2 个以上工具覆盖核心动作（如检索知识、调用业务 API）。
    • 至少 1 个工具走 MCP，验证「标准协议」带来的可替换性。
    • 处理边界：工具失败时的回退、用户确认、超时与重试。
    • 交付：能端到端跑通一个用户任务的 Demo。
    📺
    📖 学习要点（4 条）
    没有评估，AI 产品就是「凭感觉调参」。Eval 是 AI PM 的核心专业度。
    • 评估维度：准确性、忠实度(不胡编)、相关性、安全性、延迟/成本。
    • 用例集：覆盖正常/边界/对抗样本，至少 20-50 条，带标准答案或评分标准。
    • 方法：自动打分(LLM-as-judge) + 人工抽检结合。
    • 产出：一轮评估报告和「改版前后对比」基线。
    📺
    📖 学习要点（4 条）
    README 是作品的门面，决定面试官/协作者 5 分钟内的判断。
    • 架构图：用一张图讲清 用户 → Agent Loop → 工具/MCP → 模型 的数据流。
    • 使用说明：环境、运行步骤、示例对话。
    • Eval 结果：贴出关键指标与改进对比，证明你「用数据驱动迭代」。
    • 诚实写局限：哪些没做好、下一步怎么优化。

    阶段 04
    求职冲刺 · 2周 · 冲刺
    简历打磨、面试准备、作品集呈现，完成从学到用的跃迁
    📺
    📖 学习要点（4 条）
    把「我会用 AI 做产品」变成简历上可验证的事实。
    • 顶部摘要直接写 AI PM 定位 + 代表项目 + 量化结果。
    • 项目经历用「背景-动作-结果」结构，强调你设计的 Agent/RAG/Eval。
    • 技能栏区分「会用」与「能设计」：Prompt/Agent/RAG/Eval 写清到什么程度。
    • 用作品集链接(GitHub)替代空泛描述。
    📺
    📖 学习要点（4 条）
    AI PM 面试既考产品 Sense，也考对技术边界的理解。
    • 高频题类型：如何设计 AI 功能、如何评估 AI 质量、RAG vs 微调怎么选、Agent 失败怎么排查、成本与体验如何权衡。
    • 答题框架：先澄清目标与约束，再给方案，最后说如何度量与迭代。
    • 准备 1-2 个你真实做过的案例，能讲清决策链路。
    • 技术题不要求写代码，但要能和技术同学对齐语言。
    📺
    📖 学习要点（4 条）
    作品集是 AI PM 求职的硬通货，比简历更有说服力。
    • 三件套：可运行的项目(README) + 评估证据(Eval Report) + 学习轨迹(本路径本身)。
    • 每个作品写「我负责什么、用了什么 AI 能力、结果如何度量」。
    • 形式：GitHub 仓库 + 一份图文 README，方便手机/网页查看。
    • 强调「工程化思维」：你不是用工具，而是在设计系统。
    📺
    📖 学习要点（4 条）
    面试是技能，靠练出来的。
    • 每次模拟后复盘：哪类问题卡壳、表述是否清晰、案例是否讲透。
    • 用 AI 模拟可高频、低成本，重点练「结构化表达」。
    • 记录自己的回答，找出口头禅和逻辑漏洞。
    • 目标：对任何 AI PM 问题都能 30 秒内给出框架性回答。
    📺
    📖 学习要点（4 条）
    把前面的积累变成真实机会。
    • 岗位筛选：看 JD 里 AI 能力要求是否匹配你的项目。
    • 内推优先：用作品集做敲门砖，内推通过率远高于海投。
    • 投递时附一句「为什么我合适」+ 作品集链接，而不是只发简历。
    • 记录每个岗位的状态，形成简单的漏斗管理。

    高频面试题（8）
    Agent 设计设计一个客服 Agent，它需要能查订单、改地址、处理退款。你会怎么设计 Tool Use 和 Agent Loop？
    思路 思路 先画 Agent 架构图（感知→工具选择→执行→观察→循环），再定义每个 Tool 的输入输出 schema，最后设计 fallback 策略（什么时候转人工）。重点讲清楚「多轮对话的状态管理」。
    参考 架构设计： 用户消息进入后，先过意图识别（小模型/规则），判断属于查询类还是操作类。查询类直接调用对应 Tool 返回结果；操作类需要先确认再执行。 Tool 定义： ① query_order(order_id) → 返回订单状态、金额、商品列表；② update_address(order_id, new_addr) → 需要用户确认后执行；③ process_refund(order_id, reason) → 金额超过阈值需人工审批。 Agent Loop： 感知（接收消息）→ 思考（LLM 判断需要调哪个 Tool）→ 行动（执行 Tool）→ 观察（读取返回结果）→ 循环（如果需要多步则继续）。关键：每步都要记录到 context，避免重复调用。 Fallback 策略： 连续 2 次工具调用失败 → 转人工；退款金额 >500 元 → 人工审批；用户情绪检测到负面 → 转人工并标记优先级。 加分项： 提到用 Checkpointing 保存对话状态，用户中途离开再回来能接续；提到 Eval 框架评估 Agent 在 100 个测试用例上的表现。
    Eval 方法你的 AI 客服上线后准确率只有 75%，你会怎么系统性地提升？
    思路 思路 分三步：1) 建 Eval 数据集，按错误类型分类（幻觉/拒答/理解错误）；2) 分析 Top 3 错误类型的根因（Prompt/数据/模型）；3) 针对性优化并重新评估。强调「数据驱动的迭代」。
    参考 第一步：建立 Eval 数据集 从线上日志中抽取 500 条 bad case，按错误类型标注：幻觉（编造不存在的信息）35%、拒答（该回答但不回答）25%、理解错误（答非所问）20%、格式问题 15%、其他 5%。 第二步：根因分析 幻觉 35% → 根因：知识库覆盖不足，模型在知识盲区编造答案。方案：加 RAG，对高频问题补充知识库文档。 拒答 25% → 根因：System Prompt 过于保守，安全策略误伤。方案：调整 Prompt 边界，区分「不能回答」和「不需要回答」。 理解错误 20% → 根因：用户口语化表达，模型没正确理解意图。方案：加 Few-shot 示例覆盖常见口语表达。 第三步：迭代与验证 每次修改后跑 Eval 数据集，对比修改前后准确率。目标：幻觉降到 10% 以下，整体准确率提升到 88%+。上线后持续监控，建立数据飞轮——用户反馈自动进入下一轮 Eval 数据集。 加分项： 提到「不要只看整体准确率」，要分场景看（退款场景准确率可能比查询低 15%）；提到成本控制（不是所有 bad case 都值得修，按影响面排序）。
    产品策略RAG 和微调，什么场景选哪个？如果一个客户问「我的产品文档有 10 万页，怎么做 AI 问答」，你怎么回答？
    思路 思路 核心判断：知识更新频率。频繁更新→RAG（改数据库不改模型）；稳定领域+特定格式→微调。10 万页文档→RAG + 分块策略 + 向量检索，不建议微调（成本高、更新难）。
    参考 决策框架： 选 RAG 当：知识需要频繁更新、需要溯源（标注答案来自哪份文档）、数据量大且持续增长、预算有限。 选微调当：需要特定输出风格/格式、领域术语密集且稳定、推理速度要求高（微调后小模型可能够用）、有足够的标注数据。 10 万页文档的具体方案： 1. 分块策略： 按章节/段落分块，每块 500-1000 Token，保留上下文重叠 100 Token。不要按固定字数切——会切断语义。 2. 向量化： 用 Embedding 模型（如 text-embedding-3-small）对每个块生成向量，存入向量数据库（Pinecone / Milvus / Chroma）。 3. 检索策略： 用户提问 → 向量检索 Top 5 相关块 → 拼 Prompt → LLM 生成回答。加 Rerank 提升精度。 4. 为什么不微调： 10 万页 ≈ 1.5 亿 Token，微调成本高且文档更新后需要重新训练。RAG 只需更新数据库。 加分项： 提到混合方案——RAG 为主 + 微调一个小模型做意图分类/路由；提到 Eval（建 100 个标准 Q&A 对，评估检索召回率和回答准确率）；提到成本估算（每千次查询的 Token 成本）。
    Agent 设计你的 Agent 延迟太高（平均 15 秒），用户抱怨。你会从哪些维度优化？
    思路 思路 四个方向：1) 模型层——换小模型做路由，大模型做核心；2) Prompt 层——减少 Token、缓存 system prompt；3) 架构层——并行工具调用、流式输出；4) 产品层——加 loading 动画、分步展示结果。关键是先测量再优化。
    参考 模型层： 用更小的模型做路由 / 分类，只在核心步骤调用大模型；开启流式输出（streaming），让用户先看到部分结果而不是干等。 Prompt 层： 压缩 system prompt、减少 few-shot 示例长度、去掉冗余指令；把可并行的子任务拆成独立 prompt 并发调用。 架构层： 工具调用改并行（同时查订单 + 查库存，而非串行）；加结果缓存与语义缓存，相同问题不重复算；预取下一步可能需要的数据；用轻量 planner 减少规划步数。 产品层： 骨架屏 + 渐进式渲染，先出结构再填内容；乐观 UI（先显示「正在处理」）；把长任务拆成可感知的子步骤并展示进度条。 加分项： 给出「延迟预算拆解」——规划 2s / 检索 5s / 生成 8s，定位瓶颈在哪一段；用 trace（如 LangSmith）逐段监控，优先优化最慢的那一段而非整体。
    产品策略AI 产品和传统产品最大的区别是什么？用你自己的话解释。
    思路 思路 三个核心差异：1) 确定性→概率性（接受非确定性输出）；2) 功能验收→持续 Eval（永不「完成」）；3) 数据是运营工具→数据是产品本身（数据飞轮）。用具体案例说明，不要背概念。
    参考 确定性 → 概率性： 传统功能给定输入必有确定输出；AI 产品输出有方差，同一问题可能得到不同答案。PM 要接受「不完美但够用」，用置信度 / 兜底策略管理不确定性。 功能验收 → 持续 Eval： 传统产品上线即验收完成；AI 产品上线只是开始，需持续评估质量、监控模型漂移，答案可能随模型升级变好或变差。 数据是产品本身： 传统产品的数据是运营辅助；AI 产品的效果取决于数据飞轮——用户反馈、bad case、标注数据直接决定产品能力，数据闭环即核心竞争力。 加分项： 补充「安全护栏与人在回路」——高风险操作（退款、删除）必须人工确认；可解释性不是技术点缀而是用户信任机制。用「传统 PM 管功能，AI PM 管概率」一句话收尾。
    Eval 方法什么是「幻觉」？你的产品里如何检测和降低幻觉？
    思路 思路 幻觉 = LLM 生成看似合理但事实错误的内容。检测：自动（事实一致性校验）+ 人工（bad case 标注）。降低：RAG 提供事实依据、Prompt 约束（「不确定时说不知道」）、输出后校验。产品设计上让用户能纠错。
    参考 定义： 幻觉 = 模型生成看似合理但事实错误、或根本不存在的内容（张冠李戴、编造来源、虚构数据）。 检测： 自动——事实一致性打分、检索对齐度校验、NLI 自然语言推断；人工——抽样评测 + bad case 标注，建立幻觉率基线。 降低： RAG 基于可信知识库生成，让答案有出处；Prompt 约束「不确定时说不知道 / 必须引用来源」；用户纠错闭环——让真人能一键标记错误并回流训练。 加分项： 按场景设分级容忍度（闲聊可宽松、医疗 / 金融要严格）；建幻觉率 dashboard 持续监控，而不是上线一次就完事。
    技术协作你的算法工程师说「这个效果做不出来，模型能力不够」。你怎么判断他说的是真的还是推脱？
    思路 思路 三步验证：1) 要具体的 Eval 数据（准确率多少？在什么测试集上？）；2) 对比竞品/开源方案（别人做到了吗？）；3) 拆解问题（是模型能力问题还是 Prompt/架构问题？）。AI PM 不需要会写代码，但必须能看懂 Eval 结果。
    参考 要 Eval 数据： 不让对方用「感觉不行」搪塞，要求量化指标（准确率多少？在什么测试集上？和 baseline 差多少？）。AI PM 不写代码，但必须看得懂评测结果。 对比竞品 / 开源： 业界或竞品做到没？差距在哪？如果别人用类似方案做到了，那「做不出来」往往是范围或数据问题，不是能力问题。 拆解问题： 把「做不出来」拆成子问题（是模型能力、数据质量、还是架构设计？），定位真瓶颈。很多「做不到」其实是「没拆对」。 加分项： 设 1–2 天的 spike 小实验验证可行性，用数据决策而非立场；约定「做不到的判定标准」写入需求文档，避免反复扯皮。
    产品策略给你 3 个月和 2 个工程师，做一个 AI 产品 MVP。你会选什么方向？为什么？
    思路 思路 考察产品判断力。好的回答：选一个「AI 能做到、传统方案做不到」的场景（而不是用 AI 重复造轮子），有明确的 Eval 标准，MVP 范围克制（1 个核心功能 > 5 个半成品），有商业化路径。避免选太泛的方向。
    参考 选 AI 独有价值： 挑「AI 能做到、传统方案做不到 / 做不划算」的场景，而不是用 AI 重造一个表单。差异化才是 MVP 的意义。 明确 Eval： 能定义可量化的成功标准（准确率、满意度、节省时长），否则无法判断是否做对了，也无法迭代。 克制范围： MVP 只验证一个核心假设，1 个功能 > 5 个半成品；先跑通主链路再补边角。 商业化： 选有付费意愿、价值清晰场景，而非技术 demo；想清楚谁买单、为什么买单。 加分项： 用「一周出可用雏形 + 数据验证」的节奏替代「一次到位」；先拿真实用户跑通再谈扩展，避免闭门造车三个月做出没人要的东西。
